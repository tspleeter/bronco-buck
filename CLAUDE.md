## Sales Tax — Stripe Tax (Aug 2026)
- **Integration:** simplified Stripe Tax + PaymentIntents. Checkout is a custom Payment Element flow (not Checkout Sessions), so the one-line `automatic_tax` flag does NOT apply — tax is computed via the **Tax Calculation API** and linked to the PaymentIntent.
- **Flow:** `POST /api/create-payment-intent` creates the intent on mount (amount = subtotal+shipping) and now also returns `paymentIntentId`. As the customer fills the shipping address (debounced, once ZIP is 5 digits), the checkout page calls **`POST /api/calculate-tax`** → `stripe.tax.calculations.create({ line_items:[{amount:subtotalCents, reference:"bronco_buck"}], shipping_cost:{amount:shippingCents}, customer_details:{address, address_source:"shipping"} })` → updates the intent with `amount = calculation.amount_total` and `hooks.inputs.tax.calculation = calculation.id`. On the pinned API version `2026-04-22.dahlia`, Stripe **auto-commits the tax transaction on payment success and auto-reverses on refund** — no webhook, no manual `tax.transactions.create`.
- **hooks param:** confirmed present on `PaymentIntentCreateParams` AND `PaymentIntentUpdateParams` in stripe-node v22 typings; `hooks.inputs.tax.calculation` is `Emptyable<string>`.
- **Safe fallback (critical — live keys are `pk_live_`):** if the calc throws (Stripe Tax not enabled, no registration for the customer's location, unusable address), `/api/calculate-tax` resets the intent to `amount = subtotal+shipping` and **clears the tax link by passing `calculation: ""`**, then returns `{ tax:0, taxUnavailable:true }`. The checkout charges subtotal+shipping exactly as before. So this deploys **inert until Todd finishes dashboard setup**, then starts collecting automatically. The empty-string clear also prevents a stale hook from a prior address auto-committing a mismatched transaction.
- **UI:** Tax row in the order summary + confirmation email renders **only when `tax > 0`**; `Pay $X` button and recorded `order.pricing.total` use the taxed total. `OrderPricing.tax` already existed (optional). Server re-derives shipping from subtotal (`>=75 free else 8.95`) rather than trusting the client.
- **Tax codes:** none hardcoded — the calc omits `tax_code`, so Stripe uses the **account preset product + shipping tax codes** (set in Dashboard → Tax settings). `tax_behavior` defaults to exclusive (USD).
- **DASHBOARD PREREQUISITES (Todd — gate everything; without a registration, calc returns $0 in that jurisdiction):** (1) set head office / ship-from to 8 Nelke Ct, Hawthorne NJ 07506; (2) preset product tax code = general tangible goods; (3) preset shipping tax code; (4) tax behavior = exclusive; (5) **add a tax registration (NJ at minimum).** Verify with one live test order: watch for the Tax line at checkout and a matching entry on the Tax → Transactions page.

### Pending image work
- **Stand overlays learnings (July 2026):** side-view screenshots can have slight camera-orbit parallax vs originals (head shifts relative to stand). Alignment must refine on the stand band (y>850) after coarse global alignment. Light stand colors (sand) can fail diff-threshold extraction near highlights — use the black stand's alpha as the canonical stencil for all colors of the same view. Todd's Bambu layout has 4 filament slots, so non-black stand screenshots show recolored eyes — harmless, extraction only keeps the stand region.
- **Stand overlay re-alignment (Aug 2026 — "black/grey/sand don't fit right"):** the July overlays were positioned/sized to a single reference, so once stand colors went live the recolored plinth failed to fully cover the plinth baked into every body render → the match-body plinth color peeked out as a rim around the overlay. Worst on **left** (right edge ~14px short) and **right** (left edge ~3px short); front/back off by a few px. Root cause is the documented head-alignment tradeoff: side-view bodies are head-aligned, not plinth-aligned, so each color's plinth drifts a few px and no single overlay covered all of them. **Fix:** per view, computed the *union* of all 11 colors' plinth extents (both mane colors) from the body renders' fg masks in the plinth band, dropping outliers >60px from median. Fit each overlay via an axis-independent affine (translate + per-axis scale, **anchored at the plinth top so it never rides up over the neck**) so its plinth covers union+2px. Scale factors are tiny (sx 1.005–1.022, sy ≤1.008 — visually imperceptible on the flat molding). Then a **neck-protected feathered dilation** (radius 6, EDT nearest-opaque-color fill, upward growth allowed only in the outer 30% x-bands = corners, blocked in the central neck zone; alpha Gaussian-feathered 1.2px) mops up residual per-body drift. ## File Authoring Rules
- **Always write TSX/JSX files to disk first** (`cat > /home/claude/file.tsx << 'ENDOFFILE'`), then push via GitHub Contents API with `open(...,'rb')` for base64 encoding
- Never embed TSX with template literals in Python strings — backticks and `${}` get mangled
- Sleep 0.4–0.5s between sequential GitHub API pushes
- GET SHA before every PUT

## Key Learnings
- **Modals rendered inside `.site-nav` must portal to `document.body`:** the nav has `backdrop-filter: blur(24px)`, which (per spec, and enforced by Safari) makes it the *containing block* for any `position:fixed` descendant. A fixed modal overlay rendered inside the nav gets trapped in the 68px nav strip and pins to the top of the screen. `SeeCommercialButton`'s video modal uses `createPortal(modal, document.body)` to escape it. (Also: center modals with flexbox, not `fixed + translate(-50%,-50%)` — the transform makes Safari mis-place `<video>`.)
- **Amplify SSR Lambda env vars:** Console env vars do NOT reach SSR functions — use IAM compute role + SSM Parameter Store
- **GitHub Contents API push:** GET SHA first → PUT with base64 + SHA; sleep ~0.4s between pushes; token `ghp_*` classic PAT with repo scope
- **Local git auth:** Can be stale — GitHub Contents API is the reliable path
- **Amplify deploy check:** Site returns 403 to external requests — not a failure; check Amplify console
- **Preview aspect ratio:** 990/1294 (≈3/4)
- **CSS font-size % on spans** is relative to inherited font-size, not container height — use SVG text for size-relative nameplate text
- **`cqh` units** require `container-type` to be set on the parent — don't use without it
- **rembg / AI background removal** requires downloading a model (~170MB) from GitHub — blocked by network policy; use GrabCut (OpenCV) or remove.bg instead
- **White subjects on white backgrounds** can't be cleanly separated with flood-fill — use remove.bg or photograph against a dark background
